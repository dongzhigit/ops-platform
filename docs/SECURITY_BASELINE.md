# M0 安全验证基线

验证日期：2026-08-17

## 当前结论

M0 过渡镜像已经可以重复构建，但尚不满足正式生产发布条件。它可用于隔离内网中的兼容性验证，不应直接暴露到公网。

Trivy 0.65.0 对 `spug-ops:validation` 的严重和高危漏洞复扫结果如下。数量是漏洞在软件包中的出现次数，并非去重后的 CVE 数量；漏洞库更新后数字可能变化。

| 层级 | 严重 | 高危 | 有修复版本 |
| --- | ---: | ---: | ---: |
| CentOS 7.9.2009 | 0 | 163 | 46 |
| Python 依赖 | 3 | 45 | 48 |
| 合计 | 3 | 208 | 94 |

Dockerfile 纳入 CentOS 7 最终安全更新后，操作系统层严重漏洞降为 0。M1 最终镜像因恢复 Git 等发布流程必需工具，操作系统层为 163 个高危；CentOS 7 已停止安全维护，扫描器也明确提示检测结果可能不完整，因此这些更新只是过渡措施。

尚存的严重项：

| CVE | 组件 | 当前版本 | 修复版本 |
| --- | --- | --- | --- |
| CVE-2025-64459 | Django | 2.2.28 | 4.2.26 / 5.1.14 / 5.2.8 |
| CVE-2022-24439 | GitPython | 3.0.8 | 3.1.30 |
| CVE-2023-40267 | GitPython | 3.0.8 | 3.1.32 |

这些版本无法在当前 Python 3.6 技术栈中安全原地升级，必须通过 Python、Django 和相关 Channels 依赖的升级分支统一解决。

## 已通过的检查

- 环境安全配置单元测试：9 项通过。
- M1 MariaDB 集成测试：32 项通过，其中 9 项覆盖生产安全环境配置，12 项覆盖加密、对象授权、身份绑定、Redis 队列脱敏、旧私钥迁移、主密钥轮换和代理路由，11 项覆盖风险分级、双人审批、参数绑定、票据防重放、审计防篡改、操作预检、批量/文件/计划任务门禁和代理路由。
- React 生产构建通过；安全中心审批/审计页面及批量命令、文件分发、SSH 文件上传/删除、计划任务审批门禁已纳入构建产物。
- 全量 Django 迁移基线可在 MariaDB 空库安装，模型漂移检查通过。
- Python 源码编译检查通过。
- Docker Compose 配置解析通过。
- `linux/amd64` M1 镜像完整构建通过，镜像包含当前仓库后端和本地编译前端。
- M1 镜像启动、自动迁移、Nginx、API、WebSocket、Worker、Scheduler 和 Monitor 进程验证通过。
- 镜像内 Django、Channels、Paramiko、MySQL 和 LDAP 依赖导入通过。
- Shell 语法和 Git 差异检查通过。
- Gitleaks 全仓库扫描未发现泄露。

## 正式发布门禁

- 严重漏洞必须为 0。
- 有可用修复版本的高危漏洞必须修复；不能立即修复的项目需要有负责人、影响分析、隔离措施和到期时间。
- 基础镜像、Python 和 Django 必须处于官方安全支持周期。
- 依赖版本必须锁定，镜像必须在 CI 中重新构建和扫描。
- 数据库备份恢复、迁移回滚、Linux FUSE 文件分发和 TLS 反向代理必须在目标环境完成演练。

复扫示例：

```bash
trivy image --scanners vuln --severity CRITICAL,HIGH spug-ops:validation
```
